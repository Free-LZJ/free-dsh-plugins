# @free-lzj/dsh-console

**DSH 的工作台：插件有了统一的首页，通知有了统一的出口。**

装好后侧边栏第一个图标就是它。工作台的顶栏是**五个视图**：看板（默认）/ 规则 / 聚焦 / 连接器 / 应用——视觉与对话页的「对话 / 轨迹 / 上下文」同一套页签规格。**应用**是已接入工作台的插件列表（默认卡片宫格，可切列表 / 紧凑网格，支持搜索与置顶），点卡片在主区域打开那个插件的面板。**看板**是决策结果的视图：进来的工作事件先分类、再路由，最后落成卡片。**聚焦**是第二个 `main` 面板（`console-focus`），列平台已经算好的会话。同时它是**平台内核**：面板怎么接进来、通知怎么发出去，都由它事先定好的接口说了算。

工作表里只有接入过的插件——没接入的第三方插件不会出现在应用视图，工作台不枚举 profile 里装了什么。所以「工作台里有什么」完全由各插件自己声明，不由 dsh 加载了什么决定。

## 能力

### 1. 面板接入契约

插件不再自己抢侧边栏，而是声明「我是工作台的一个面板」：

```ts
import { useConsolePanel } from '@free-lzj/dsh-console/contract'

export function apply(ctx: ClientContext): void {
  useConsolePanel(ctx, {
    id: 'mail',                       // main 槽的键，工作台按它打开面板
    title: () => t('panel'),
    description: () => t('description'),
    keywords: () => ['mail', 'imap'],
    order: 20,
    render: MailPanel,                // 面板本体；布局照常给它 main 的两个席位
    icon: <MailIcon />,
  }, {
    locale: NS,                       // 没有工作台时，退回自己的侧边栏入口
    order: 40,
    label: () => t('panel'),
    Icon: MailIcon,
  })
}
```

两种模式由**运行时**决定，不是编译期开关：

| 模式 | 什么时候 | 结果 |
|---|---|---|
| **接入** | 组合里有工作台 | 插件交出侧边栏那一格，只在工作台首页出现；面板本身（`main:<id>`）**保留**，工作台按这个键打开它 |
| **独立** | 没有工作台 / 工作台被禁用 | 插件保留自己的侧边栏图标与面板，行为和装工作台之前完全一样 |

判断不是「启动时看一次」：Loader 行的顺序由用户的 profile 决定，工作台可能**晚于**插件挂载；工作台被禁用时插件也要把侧边栏还回来。所以契约用 `ctx.inject` 跟随服务出现/消失，这条路径有专门的测试。

契约产物（`@free-lzj/dsh-console/contract`）是**普通模块**：消费方打包时把它内联进去，所以插件不需要工作台在页面的 module table 里，也**不产生运行时依赖**——没装工作台照样能装上。

### 2. 通知接口 + 可替换渠道

任何插件（Host 半边）都能把一条通知交给工作台统一处理：

```ts
await ctx.console?.notify({
  title: '新邮件',
  body: '来自张三：季度评审改到周四',
  tone: 'info',
  source: 'mail',
})
```

工作台决定「怎么告诉用户」：渠道是一组**策略**，注册在内核里、由配置多选启用。

### 3. 任务看板

看板是工作台的第一个视图：一行状态条（待我决定 / 正在跑 / 今日完成 / 异常）+ **待办 / 进行中 / 已处理**三列，每列有名称、计数、一句说明与空态。卡片按五行解剖：来源与单号与优先级、标题、描述、类型与置信度与规则版本、执行器与状态与最后活动；置信度低于 0.6 的卡上直接写明「低于阈值，未自动派单」。操作条（派单 / 详情 / 移到…）常显——隐藏过一版，card 底部空出一条按钮高的白带，比少几个按钮更难看。

移列两条路都通：HTML5 拖拽（列在悬停时高亮），以及卡片上的「移到…」菜单——**拖拽不可键盘化，所以菜单不是备选而是等价路径**。卡片详情走 `Modal`（DSH 没有 Drawer 原语），里面是分类结果、判断依据、流转时间线与动作；卡片有会话时还带只读日志与插话输入框。

「已处理」列按天折叠：今天展开，更早的每天一行，点开才列——找历史靠搜索，不靠一直往下滚。键盘走位是 `j` / `k` 在**屏幕上可见的**卡片之间移动焦点（折叠起来的卡不在其中）、`Enter` 开详情、`Esc` 关。

### 4. 规则视图

工作台第四个入口以外的那一页（`规则`）：**规则文件里现在有哪些规则**、每条规则的条件与动作（动作带 `自动 / 建议 / 关闭` 三态）、规则顺序与启停，以及引擎最近对哪些邮件做了什么、还能不能撤销。

引擎本身还在 `@free-lzj/dsh-mail` 里（P1a 才会抽成独立包），所以这一页读的是它已经公开的 HTTP 面，不复制规则状态：只要改完立刻回读，页面上看到的永远是引擎手上的那一份。

改**条件**不在这页做：规则是磁盘上的文本，条件怎么写属于编辑文件，所以每条规则带一个「复制修改指令」——把规则当前定义和文件路径拼成一段话进剪贴板，粘给 agent 就行；剪贴板拿不到（非安全上下文）时退化成把整段指令显示出来，不静默失败。页面底部另有规则原文（`<details>`，只读），要看文件真正长什么样不必去翻磁盘。

**试跑**在每条命中记录上：记录里已经带着那封邮件在哪（账号 / 文件夹 / uid），所以不用再给一个「选邮件」的控件——点一下拿那封邮件重跑当前规则，就地回答「会命中哪条、会做什么、为什么」，**不改动任何邮件**。

事件模拟器（投递一个事件，看它怎么分类、路由、建卡）住在**连接器视图**的开发工具区，并标注「调试用」；连接器清单也在那里。

流转是「确定性外壳 + 判断核 + 路由表」三层，和通知渠道一样的策略 + 注册表写法：

| 层 | 是什么 | v0 的实现 |
|---|---|---|
| 分类核 | 判断事件是什么任务 | 规则分类器（关键词打分，附置信度与理由）；大模型分类器是以后实现同一接口的另一个实现 |
| 路由表 | 判断之后怎么办 | `$DSH_HOME/dsh-console/routing.json`，改完自动热加载，不用重启 |
| 执行器 | 派给谁干活 | `dsh` / `codex` 两个 id，目前都是**模拟执行器**：跑固定脚本、写日志，不调模型、不碰工作区、不写任何外部系统 |
| 连接器 | 事件从哪来、结果往哪去 | `mail` / `webhook` 有入口（ingest 路由），`dingtalk` / `jira` 是占位：列出来、可配置，但不发真实请求 |

规则只有三条硬线：置信度低于 0.6 的卡一律不自动派，落进待办等人工；同一来源同一外部 id 重复投递不重复建卡；**完工的卡只进「已处理」并标「待确认回写」，不自动回写任何外部系统**。审 diff 关口是用户明确暂缓的，v0 没有。

事件入口有两条：页面上的事件模拟器，和 Host 上的 `ctx.console.ingestWorkbenchEvent(event)`（邮件这类插件以后从这里转交；调用前先探有没有这个方法，没有就是没挂看板）。

| 渠道 | 行为 |
|---|---|
| `desktop` | 走浏览器 Web Notification，在 Windows 通知中心弹出（需要授权） |
| `inapp` | 工作台通知中心：铃铛角标 + 列表 |
| `sound` | 一声短提示音 |

- 前两个渠道**只在有页面打开时**才计划投递（`plan()` 会回答否），因此不会「通知丢掉还不知道」。需要一个「没开页面也能送达」的渠道时，注册一个新的实现即可——见下面「加一个渠道」。
- 一条通知可以同时走多个渠道；某个渠道失败只影响它自己，`notify()` 不 reject，通知照常进中心。
- 至少保留一个渠道：设置行的最后一个开关是锁住的。
- 配置里出现本版本不认识的渠道 id（升级删了实现）会被丢弃并告警，不会让配置整个失效。

### 5. 条目契约：通知能被「处理」

`notify` 是一条**一次性通知**：收完就完了，不能标记已处理、不能点、不能追责。需要用户做一个决定时用 `raise`——它多给两样东西：**身份**（返回的 id）与**状态**。

```ts
const item = await ctx.console?.raise({
  title: '建议归档这封推广邮件',
  body: '规则「推广与电子报」建议执行 move',
  source: 'mail',
  kind: 'mail',                     // 谁举起的：点按钮时路由回它
  actions: [
    { id: 'apply', label: '执行', style: 'primary' },
    { id: 'skip', label: '不用' },
  ],
})
```

举起方注册「用户点了我的条目」的处理器：

```ts
ctx.console?.onAction('mail', async (item, actionId) => {
  if (actionId !== 'apply') return
  // 真正把事做掉；抛出的错误会显示在条目旁边，而且**条目不会被标成已处理**
})
```

| 能力 | 说明 |
|---|---|
| `raise(notice)` | 建一条条目；`notify` 就是它的退化形态（没有动作） |
| `onAction(kind, handler)` | 按 `kind` 注册处理器；重复注册后者生效，注销后点击被拒绝 |
| `actOn(id, actionId)` | 用户点了某个动作。**处理器成功才标 `resolved`**——失败必须留在队列里 |
| `dismiss(id)` | 用户说「不是我的事」 |
| `snooze(id, until)` | 到某个时刻之后再出现 |
| `state().awaiting` | 还等着用户的条数（Host 算的，被 snooze 的不算） |

三条设计上不肯让步的地方：

1. **工作台不知道任何动作的含义**：它只把 `(条目 id, 动作 id)` 交回举起它的插件。所以加一种新动作不需要改工作台。
2. **动作失败时条目不消失**：否则界面会告诉用户「处理了」，而实际没有。
3. **`awaiting` 由 Host 算**：每个界面显示同一个数，也不会把 snooze 到明天的算成待处理。

首页的第一块从「插件目录」换成了**注意力队列**（下面是 `state().running` 提供的「正在跑的会话」）：工作台要回答的第一个问题是「现在需要我决定什么」，插件目录是手段不是目的。

### 6. 自动化日志：它做过的事

有些事不需要人决定，只是「我顺手做了」——归档一封推广、标记一条通知。这类事**不该进队列**（一天二十封就是二十条打扰），所以走另一条通道：

```ts
ctx.console?.log({
  source: 'mail',
  title: '按「推广与电子报」处理了：限时优惠',
  detail: '已标记为已读；已移动到「推广」',
  ok: true,
})
```

- 只进首页的**自动化日志**（默认折叠在队列下面，最近 5 条），封顶 100 条，不打角标、不计入 `awaiting`、不投递任何渠道。
- `ok: false` 表示「试过但失败了」，日志里标成警告色——日志不能读起来像成功。
- 它不是审计台账：完整历史留在做事的那个插件里（例如邮件插件自己的命中记录）。

### 7. agent 可调用的两个工具

除了插件之间调的 `ctx.console`，Host 半边还给**会话里的 agent** 注册了两个工具（走 `ctx.tools`，同样按可选依赖处理）：

| 工具 | 用途 | 关键约束 |
|---|---|---|
| `console_notify` | 让 agent 主动推一条通知（桌面通知 + 通知中心 + 提示音） | 不阻塞、不等人回答；需要人做决定时仍然要在对话里问 |
| `open_session` | 在一个已存在的工作目录里建工作区并开会话，把 `prompt` 作为第一条消息投递进去 | `cwd` 必须是**已存在**的绝对路径；本工具不建目录 |

`open_session` 解决的是「活要落在某个具体仓库里干」：会话的工作目录在创建那一刻就定了，所以想在读完工单 / 读完邮件之后再决定去哪个仓库，只能让当前会话用这个工具开下一跳。顺序与邮件插件的会话动作一致——先建会话、再挂工作区、改名，最后投递消息。

缺 `tools` 时不注册（只记一行日志）；缺 `sessionController` / `workspaceRegistry` 时 `open_session` 报「未挂载」，不会建出半成品会话。

## 安装

```sh
# Web
dsh plugin --profile web add @free-lzj/dsh-console

# 桌面端
dsh plugin --profile desktop add @free-lzj/dsh-console
```

本包自带 `dsh.bundle`，`dsh plugin add` 已经插入 `console` 这一行，所以 profile 补丁里**不用也不要**再手写同 id 的 `- insert:`（同一个 id 两行 → 插件市场预检报 `duplicate loader entry id` 并回滚安装）；要覆盖配置就写一行同 id 的 override（`- id: console` + `config:`，**不带** `insert`）。

dsh plugin --profile desktop add "<本仓库绝对路径>/packages/console"

## 配置

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `channels` | `('desktop' \| 'inapp' \| 'sound')[]` | 全部三个 | 通知走哪些渠道。设置 → 通用 → **通知** 里多选，写回这一行 |
| `layout` | `'grid' \| 'list' \| 'compact'` | `grid` | 首页布局。首页右上角切换，写回这一行 |
| `workbenchConnectors` | `('mail' \| 'webhook' \| 'dingtalk' \| 'jira')[]` | `['mail', 'webhook']` | 看板启用哪些连接器；写了实现里没有的 id 会被丢弃并告警 |
| `workbenchClassifier` | `string` | `'rule'` | 看板用哪个分类器；写了没注册的 id 会回落到规则分类器并告警 |

页面的置顶与「上次停在哪一页」（`$DSH_HOME/dsh-console/prefs.json`）不在这一行里：它们是**用户点击产生**的状态，不是配置。

## 工作台里的界面

界面跑在 DSH 的页面里，所以完全用 DSH 的设计系统（`ui-primitives` 控件 + `--dsw-*` token），不另起一套；约束见 [`rules/plugin-ui.md`](https://github.com/Free-LZJ/free-dsh-plugins/blob/main/rules/plugin-ui.md)。

- **页头 + 视图导航**：页头左侧页面标题 16/24、字重 500，右侧是通知按钮；导航条 1:1 复刻对话页页签——`gap: 36px`、13/16 字重 500、tertiary，选中项用 `--dsw-alias-state-business-primary` + 2px 底条，底部一条 0.5px 发丝线（`--dsw-alias-border-l3`）。导航是 `Button` + `aria-current="page"`，不声明 `role="tablist"`（那是 `ui-primitives` 的语义）。
- **看板**：状态条与三列卡片，卡片用 DSH 的设置卡片材质（R20 + `--dsw-alias-settings-card-fill` / `--dsw-alias-settings-card-stroke`）；状态永远带文字，不只靠色点。
- **应用**：已接入的插件卡片。标题 14/20 字重 500、说明 12/18 tertiary；卡片末尾的「⋯」`Menu` 里是**置顶 / 取消置顶**。搜索与三种布局的 `SegmentedControl` 收在这一视图里，不再占页头。
- **通知中心**：通知按钮上的角标 + 下拉列表，可清空。
- **设置 → 通用 → 通知**：渠道从多选下拉里选（`Menu` 的 `selectedIds`）。设置行用 DSH 的设置行几何——标题 14/22、说明 12/18 tertiary、`padding: 16px 0`、`border-bottom: 0.5px solid var(--dsw-alias-border-l2)`。

## 谁的数据在哪一半

列表不是 Host 下发的：面板的标题、说明、顺序、图标都由**接入插件自己的浏览器半边**声明，只有那一侧能渲染它们；Host 只保存置顶 id 列表和通知、渠道、布局。浏览器把两边拼成卡片，所以「工作台显示哪些插件」这件事没有第二份真相。

## 给插件作者：三个扩展点

| 想做的事 | 用什么 |
|---|---|
| 把面板接进工作台 | 浏览器半边 import `@free-lzj/dsh-console/contract` 的 `useConsolePanel` |
| 发一条通知 | Host 半边 `ctx.console.notify({...})`（可选依赖，用 `?.`） |
| 加一个通知渠道 | 在本包里 `ctx.console.channels.register({ id, plan, deliver })`，再在设置行加一个名字 |

前两个是给外部插件的稳定接口；第三个目前是包内扩展点（渠道实现在 `src/builtin-channels.ts`，注册在 `src/index.ts`）。加渠道**不需要**改通知派发逻辑——派发只认识接口。

## 数据边界

- **路由**：`/dsh-console/state`（读快照）、`/dsh-console/events`（SSE：状态与通知）、`/dsh-console/config`（写配置）。读路由只回答同源请求；写路由额外要求 `x-dsh-console: 1` 与 JSON content-type——跨站表单发不出这个自定义头。看板另有三条：`/dsh-console/workbench/state`（读看板）、`/dsh-console/workbench/ingest`（投递事件）、`/dsh-console/workbench/action`（派单 / 移卡 / 插话 / 暂停 / 继续 / 结束），同一套守卫；其中 ingest 目前只接受同源请求，外部 webhook 接入要先补签名校验。
- **状态**：`$DSH_HOME/dsh-console/prefs.json`（置顶 id 列表 + 当前视图），权限 `0600`，写盘走临时文件 + `rename`；读到坏 JSON 回落为空而不是让插件起不来。当前视图只有四个值住在 `main:console` 里，`focus` 对应第二个 `main` 面板 `console-focus`——切到它是 `ctx.layout.selectPanel`，而布局不持久化，所以刷新后靠这个字段恢复。看板另有 `$DSH_HOME/dsh-console/workbench.json`（卡片与会话，同一写法）和 `routing.json`（路由表，缺失时写入默认表，改坏时沿用上一版并告警）。
- **通知**：只存在内存里（本次运行，最多 50 条），重启即清空；不落盘、不外发。
- **卡片审计**：每张卡存着路由决策（动作、执行器、路由 id、路由表版本、分类与理由），路由改了可以拿同一批事件重放对照。

## 已知限制

- **规则视图依赖邮件插件**：规则、命中记录与撤销都在 `@free-lzj/dsh-mail` 的 triage 引擎里，这一页读的是它自己的路由（`/dsh-mail/triage/*`）。没装邮件插件时这页只说「引擎没加载」，不画空列表——「没有规则」和「没有引擎」是两件事。P1a 把内核抽成 `@free-lzj/dsh-decision` 之后，换的是 `src/client/rules.tsx` 里那个数据源，不是这一页。
- **规则视图只读回来了最近 20 条命中**：引擎最多给 100 条，页面画 20 条再报一句「共 N 条」；再往前翻要等搜索/分页，v0 不做。
- **看板执行器是模拟的**：`dsh` / `codex` 目前只跑固定脚本、不调模型、不改代码；接真实 agent 是以后实现同一执行器接口的事，不是改看板。
- **看板不自动回写**：完工的卡只标「待确认回写」，钉钉 / Jira / 邮箱的出站动作都没有接；确认后回写的流程等用户定。
- **看板没有审 diff**：用户明确暂缓，v0 的「已处理」只表示 run 跑完了，不表示 diff 被审过。
- **钉钉与 Jira 是占位**：看板里列得出、配得上，但不发真实请求；它们的事件目前只能经 ingest 路由以对应来源投递演示。
- **接管只到侧边栏那一格**：侧边栏面板列表是平台的一个列表槽，没有按 id 过滤的入口。所以接入工作台的插件交出的只是**侧边栏那一格**；它在 `main` 上的面板仍然存在（正是工作台打开它的方式）。别的插件若在别处放了自己的入口，工作台管不到。
- **列表里只有接入过的插件**：这是刻意的——工作台不枚举 profile，也就不会列出、更不会「内嵌」没接入的插件。它们照旧从自己的侧边栏入口进入。
- **通知没有历史**：不落盘，也没有「已读」状态；清空就是清空。
- **桌面通知需要授权**：浏览器拒绝后 `desktop` 渠道投递失败（仅影响它自己），设置行会说明原因。授权只能由用户在浏览器里给。
- **`plan()` 需要页面在场**：`desktop` / `inapp` / `sound` 都要求至少一个工作台页面在流式接收事件；没有页面时投递为空（通知仍进内存）。这是「页面才能弹通知」的物理限制，不是遗漏。
- **契约是内联的**：改契约（`src/client/contract.ts`）之后，消费方要**重新构建**才拿到新版；契约的产物形状有测试兜底，但版本对齐靠各自发版。

## 开发

```sh
pnpm --filter @free-lzj/dsh-console run typecheck
pnpm --filter @free-lzj/dsh-console run build

# vitest 的 include 是仓库根相对路径，测试要从仓库根跑
pnpm exec vitest run packages/console
```

测试不连网、不弹真通知：渠道用注入的 `PageSurfaces` 假实现，页面事件流用真的 SSE 编解码但由测试驱动 `EventSource`，契约的两种模式跑在真的 cordis Context + 真的插槽注册表上（注册表取自渲染器浏览器半边，不是替身）。
