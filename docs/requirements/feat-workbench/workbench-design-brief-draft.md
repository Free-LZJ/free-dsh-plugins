# 工作台设计简报（草稿 · 2026-10-25）

来源：用户 2026-10-24 晚在主聊天里的口头描述 + 当晚助手给出的参考方案整理而成，尚未经用户确认。**只聊样子、不要求实现。**

## 用户已定的形状

- 现状：仓库里已有工作台插件雏形，目前只有约邮件功能。
- 连接器 = 入口 + 出口：邮件、webhook、钉钉消息、Muse 现有连接器；以后加新渠道只接新连接器，不改核心。
- 首页 = 看板：待办 / agent 当前处理 / 已处理 + DSH 当前运行会话的聚焦视图。
- 规则 = 可配置：收到 Jira 工单 → 派给本地 agent（DSH 或 Codex，不写死、可拓展）；agent 按工单内容处理，一般是 bug 单。
- 规则会经常改，且多数判断要交给大模型（如判断 Jira 工单属于什么任务）；太复杂的规则引擎不好维护，这一点尚未定怎么做。

## 建议的 v0 形状（抄作业版，取自 2026-10-24 晚的讨论）

1. **确定性外壳 + 大模型判断核**，不先上可视化规则编辑器：
   - 硬规则（极少、几乎不改）：来源白名单、去重、限流、危险动作必须审批、预算上限。
   - 判断（大模型分类器，小模型即可）：输出任务类型（bug/需求/咨询…）、项目、优先级、建议派给哪个 agent、置信度、理由。改规则 = 改提示词 + 换例子，不是改条件树。
   - 路由表（YAML/JSON 数据、热加载）：如 bug → 修 + 跑测试；咨询 → 只回钉钉、不派活。
   - 兜底：置信度低的一律不自动派，落进看板「待办」当人工溢出池。
2. **看板形态抄 Kanbani**：一个任务一个 git worktree，agent 并行不打架；看板里直接看 diff，合并/丢弃由人定。
3. **连接器层抄 Composio 的 trigger / tool 分离**：进来的是事件，出去的是动作，认证托管、统一调用。
4. **可追溯**：每张卡记下「哪个版本的规则/提示词派的」；用 EXEPD 历史 bug 单建评估集，改规则先跑一遍回归。

## 参考：AgentsRoom 看板（2026-10-26 补充，用户确认可借鉴）

来源：AgentsRoom backlog task board（拖卡进进行中即启动 agent 的看板产品）。对照后值得借鉴的：

1. **拖卡即启动**：规则自动派单之外，拖动就是手动派单入口——低置信度落进待办的卡，人工拖一下即可开工。
2. **卡片实时状态**：工作中 / 等待输入 / 完成等状态直接贴在卡片上；DSH 会话聚焦视图不必单独成页，状态先贴卡片，点卡再看详情。
3. **差异视图审阅**：改完先审 diff，满意才算完成；原建议审阅应成为到「已处理」的必经关口，但用户 2026-10-26 明确表示审 diff 暂时不用——此项暂缓，不进 v0。
4. **导入只读不回写、反复导入不重复**：从 Jira、邮件拉单时，源端状态只由出口动作改动，避免导入误改源单；去重键防止同一工单重复建卡。

不太适合照搬的：

1. **只有进行中列能启动 agent**：本方案规则自动派单才是主路径，拖卡只是补充，照搬会打乱自动派单的流转语义。
2. **17 种 agent 与云端同步**：本方案核心是本地 DSH、Codex 这类可拓展执行器，贪多抬高维护成本，云端同步也不符合本地优先的取向。

## v0 先做 / 后做（建议，未定）

- 先做：连接器抽象（事件/动作）+ 看板四列 + 硬规则 + 大模型分类 + 路由表 + 低置信度进待办。
- 后做：可视化规则编辑器（等规则多到管不过来时）、自然语言意图式规则（GitHub Agentic Workflows 那种，等分类稳定了再靠）。
