# 设计模式与扩展点

**何时加载**：新增/修改任何「可替换实现」「多选配置」「跨插件接口」时——例如通知渠道、导入源、面板接入、存储后端、搜索/抓取 provider；以及评审这类代码时。

仓库里已经出现过两次同一种形态（`agent-import` 的导入源、`console` 的通知渠道），所以把它固化成规则，避免下一个特性又写成一排 `if`。

## 一个能力有多种实现时

必须按这四层拆开，缺一层就算没拆：

| 层 | 是什么 | 判断标准 |
|---|---|---|
| **契约** | 一个只描述行为的接口（如 `NotificationChannel { id, plan, deliver }`） | 接口里没有 `switch`、没有具体实现的名字、没有配置读取 |
| **实现** | 每个具体做法一个模块/函数（桌面通知、应用内、提示音） | 新增一个实现只新增文件，不修改内核 |
| **注册表** | 内核持有的集合，按 id 注册与取出 | 内核里**没有**实现名的列表；实现由装配处注册 |
| **配置** | 用户多选「启用哪些」（下拉/多选，不是代码常量） | 能力的存在与否由注册表决定，是否启用在配置里；两者互不推导 |

对应模式名：**策略（Strategy）+ 注册表（Registry）**。通知中心这类「订阅变化再刷新界面」的部分是**观察者（Observer）**；`ctx.console` 这类「一个入口收所有请求」的门面是**外观（Facade）**。

**可机械判断的检查**：

- 内核文件里出现任一实现的名字 → 违反（例如 `notify` 里写 `if (id === 'desktop')`）。
- 新增一个实现需要改内核文件 → 违反。
- 接口里能读到 `config` / 环境变量 / 权限状态 → 违反（这些属于实现内部或调用方）。
- 配置只能选「开/关整个能力」而不能选「用哪一个」→ 违反。

## 契约放在哪

- 跨插件的契约必须**从包导出**（如 `@free-lzj/dsh-console/contract`），消费方 import 它，不 import 实现模块。
- 浏览器半边被**内联**到消费方 bundle：契约产物不得有运行时外部依赖，也不得注册进页面的 module table（有产物契约测试兜底，见 [`testing.md`](testing.md)）。
- 契约里只放类型、常量、纯函数；注册逻辑放在独立的入口文件，避免类型-only 模块被迫带上运行时。

## 可选依赖与可拔插

- 消费方**不得**把可选插件写进 `dependencies`/`peerDependencies` 来「保证它在」；能力缺失必须是正常状态。
- 用 `ctx.get('名字')` 探测，用 `ctx.inject(['名字'], …)` 跟随（服务出现时启用、消失时回退）——**判断一次是不够的**：Loader 行的顺序由用户的 profile 决定，插件可能先于提供者加载。
- 回退路径必须真的可用（例如没有工作台时面板仍有自己的侧边栏入口），不能只是「不报错」。

## 与配置文件的关系

- 实现清单写在装配处（`src/index.ts` 的注册），不写在 schema 里；schema 只描述「已启用哪些 id」。
- 配置里出现内核不认识的 id（跨版本升级、实现被删）应当**丢弃并告警**，而不是让整个配置不可用。
